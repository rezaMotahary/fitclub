# داده روی سرور — قانون دائمی

آخرین به‌روزرسانی: 2026-11-01  
تأیید مالک: ۱۴۰۴/۰۸/۱۰ (چت PM)

این قانون از قانون لوکال جداست. روی سیستم برنامه‌نویس می‌شود دادهٔ نمونه را پاک و دوباره ساخت. **روی سرور هرگز.**

---

## قانون اصلی

روی محیط اصلی / سرور:

1. **داده نباید از دست برود.** آپدیت برنامه نباید اعضا، پرداخت، حضور، اشتراک، یا حساب‌ها را پاک کند.
2. **دادهٔ فیک لوکال نباید روی سرور باشد.** داستان‌های نمونه (سارا با بدهی روز ۱۶، چند عضو نمایشی، حضور جعلی، چارت شش‌ماههٔ ساختگی، …) مخصوص لوکال است.
3. **آپدیت فقط افزایشی است.** جدول جدید و ستون جدید با مهاجرت (`prisma migrate deploy`) اضافه می‌شود؛ `seed` پاک‌کننده اجرا نمی‌شود؛ `deleteMany` روی کل دیتابیس ممنوع است.
4. **پشتیبان قبل از هر آپدیت سرور.** اگر آپدیت شکست خورد، داده برگردد؛ از نو ساختن دیتابیس به‌جای پشتیبان ممنوع است.

---

## حساب‌های مجاز روی سرور (برای تست)

فقط این سه نقش، هر کدام **یک** حساب — نه لیست اعضای نمایشی:

| نقش | تعداد روی سرور |
|-----|----------------|
| مدیر | ۱ |
| منشی | ۱ |
| عضو | ۱ (برای تست ورود) |

پلن‌های ۲ / ۳ / ۴ / هر روز می‌توانند به‌عنوان تعرفهٔ خالی باشگاه وجود داشته باشند (قیمت را مدیر عوض می‌کند). عضو تست لازم نیست تاریخچهٔ حضور و بدهی ساختگی داشته باشد مگر مالک بعداً بگوید.

ساخت این سه حساب باید **اگر نبودند اضافه شوند** (upsert). اگر بودند دست نخوردند — رمز را بی‌جهت عوض نکن مگر مالک بخواهد.

## ممنوع روی سرور

- `npx prisma db seed` که اول همه را `deleteMany` می‌کند  
- اجرای دوبارهٔ seed لوکال حتی با `DEMO_MODE=true`  
- ری‌ست دیتابیس برای «تمیز کردن»  
- `migrate reset` / drop database  
- کپی کردن دادهٔ فیک از سیستم شخصی به سرور  

`DEMO_MODE` فقط یعنی: کد ورود `123456` و صفحهٔ `/how-to-open` برای آموزش باز باشد. **اجازهٔ پاک کردن داده نیست.** → `docs/security.md`
