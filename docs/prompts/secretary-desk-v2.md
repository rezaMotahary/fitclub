## هدف
تکمیل پنل منشی تا پذیرش یک باشگاه واقعی باشد — نه فقط صفحهٔ حضور جدا از صفحهٔ پرداخت.

وضعیت الان:
- `/secretary` = فقط حضور (AttendanceDesk)
- `/secretary/payments` = قسط/تسویه/تمدید (PaymentDesk)
- فروش اشتراک اول، ثبت عضو جدید، آرشیو/فعال‌سازی در UI منشی یا غایب است یا از مسیر پذیرش جداست (`StaffDesk.tsx` اگر هنوز استفاده نمی‌شود، ادغام/جایگزین کن — کد مرده نگذار)
- مدیر v2 (`/admin`) تأیید QA شده؛ ظاهر کامل هر سه پنل هنوز نوبتش نیست (`docs/ui-ux-panels.md`) — این کار بازطراحی گرافیکی همهٔ پنل‌ها نیست

## رفتار درست (طبق docs)
منبع حقیقت: `docs/business-rules.md` · `docs/user-flows.md` · `docs/user-roles-permissions.md` · `docs/sample-data.md` · `docs/theme.md` · `docs/project-identity.md`

منشی باید در پذیرش بتواند بدون گیج شدن:
1. عضو را با نام / کد FS- / موبایل پیدا کند (رقم فارسی و انگلیسی).
2. همان‌جا وضعیت را ببیند: پلن، پایان شمسی، بدهی، مانده/سقف هفته، داخل بودن، سانس، آیا ورود مجاز است یا دلیل رد.
3. ورود/خروج/ابطال همان روز را بزند (منطق حضور فعلی را نشکن).
4. عضو جدید ثبت کند (نام، موبایل، سانس/جنس طبق مدل موجود) و کد FS- سیستم بسازد.
5. فروش اشتراک اول را ثبت کند (حداقل نصف؛ شروع امروز یا آینده نه گذشته) + پرداخت نقد/کارت‌خوان/کارت‌به‌کارت.
6. قسط/تسویه و تمدید را همان قوانین فعلی Payments انجام دهد (KI-004…007 را نشکن: select تم تاریک، مبلغ با جداکننده+حروف، پلن تمدید پایدار، تعویض عضو پایدار).
7. آرشیو / فعال‌سازی دوباره طبق قانون (حذف نیست).

ورود/خروج فقط منشی. مدیر می‌تواند حضور را ببیند و همان روز ابطال کند؛ ثبت ورود/خروج مدیر ممنوع بماند.

## پیشنهاد محصولی (حداقل حدس)
یک خانهٔ پذیرش برای منشی بساز (`/secretary`) با چند بخش واضح روی یک جریان، نه سه جزیرهٔ بی‌ربط:
- پیدا کردن / انتخاب عضو
- کارت وضعیت همان عضو
- کارهای همان لحظه: ورود یا خروج · پرداخت/تمدید · فروش اگر اشتراک جاری ندارد
- ثبت عضو جدید
- لاگ امروز / داخل سالن (همان حضور فعلی)

مسیر `/secretary/payments` می‌تواند بماند (لینک) ولی کار اصلی از خانهٔ منشی بدون گم شدن انجام شود.
چیدمان دسکتاپ کمی جادار (`desk-shell-wide` مثل مدیر) خوب است؛ بازنگری UI/UX کامل نکن.

## تست
- تست واحد/API برای ثبت عضو و فروش اگر منطق جدید جدا شد.
- e2e یا تست UI در حد الگوی پروژه.
- رقم فارسی و انگلیسی برای موبایل و مبلغ.
- دادهٔ نمونه: صفحه خالی ممنوع؛ عضو جدید بشود ساخت؛ فروش برای عضو بدون اشتراک جاری قابل تست باشد (اگر seed ندارد، یک عضو نمونهٔ بدون اشتراک جاری اضافه کن و در `docs/sample-data.md` بنویس).
- regression: حضور (سقف، بدهی روز ۱۵، ابطال) · پرداخت · تمدید پلن متفاوت که نپرد · KI-003 مدت حضور.
- همهٔ تست‌های مرتبط را خودت اجرا کن؛ با تست قرمز push نکن.

## ممنوع
- پرداخت آنلاین، ثبت‌نام از سایت، ورود توسط مدیر، مهمان، گزارش هزینه، پنل مربی
- عوض کردن قانون بدهی/نصف/سانس/هفته
- بازطراحی ظاهر هر سه پنل
- scope creep
