## ۱) پیام‌ها — KI-015 (الزامی)

الگو همان پنل مدیر است: `SectionNotice` در `AdminDesk.tsx`. هر پیام زیر همان بخش.

- نتیجهٔ جستجو (پیدا شد / پیدا نشد / خطا) زیر جعبهٔ جستجو.
- ورود، رد ورود، و خروج کنار کارت همان عضو و دکمه‌هایش — نه بالای آمار کل صفحه.
- ابطال کنار همان ردیف لاگ، یا اگر جا تنگ است بالای همان بخش «لاگ امروز»، نه بالای صفحه.
- ثبت عضو جدید کنار فرم عضو جدید.
- فروش / قسط / تمدید کنار همان فرم. اگر این فرم‌ها را به خانهٔ منشی آوردی، پیام را همان‌جا نگه دار.
- آرشیو / فعال‌سازی کنار همان عضو.
- فقط خطای «صفحه اصلاً بالا نیامد / ارتباط اول بار قطع است» می‌تواند یک نوار بالای صفحه باشد.

یک پیام موفق ورود نباید جستجو و لاگ را هم قاطی کند. با کار بعدی، پیام کار قبلی همان بخش پاک یا جایگزین شود تا دو پیام کهنه روی هم نمانند.

## ۲) صفحه‌بندی — KI-016 (الزامی)

از `DeskPager` موجود استفاده کن. ظاهرش همانی است که مالک در پنل مدیر تأیید کرد:

- نوار **زیر لیست**، با فاصله، جدا از عنوان.
- دکمه‌ها به هم و به متن نچسبند. روی اسم عضو یا فیلد فرم نیفتند (درس v0.9.3).
- قبلی / شمارهٔ صفحه / بعدی. صفحهٔ اول و آخر حالت غیرفعال واضح.
- اگر فقط یک صفحه است، نوار را نشان نده.
- تم روشن و تاریک، دسکتاپ و موبایل، RTL.

این لیست‌ها صفحه می‌خواهند:

- نتیجهٔ جستجوی عضو در پذیرش. API از قبل `page` و `pageSize` دارد (`searchMembers`). سقف ۱۲تاییِ بی‌خبر را بردار. حدود ۸ نفر در هر صفحه کافی است؛ بقیه با صفحهٔ بعد بیایند، غیب نشوند.
- لاگ امروز. اگر API کل روز را یکجا می‌دهد، صفحه‌بندی سمت صفحه با همان `DeskPager` قبول است.
- «الان داخل سالن» اگر از یک صفحه بیشتر شد.
- سوابق پرداخت، اگر خانهٔ منشی آن‌ها را نشان داد. در `/secretary/payments` از قبل هست؛ همان را حفظ کن.
- هر لیست عضو/آرشیو جدیدی که به پذیرش اضافه می‌کنی.

لیست خیلی کوتاه (یک یا دو نفر داخل سالن) صفحهٔ الکی نمی‌خواهد.

## ۳) خانهٔ پذیرش

`/secretary` باید پذیرش واقعی باشد، نه فقط صفحهٔ حضور جدا از پرداخت.

منشی بدون گیج شدن بتواند:

1. عضو را با نام / کد FS- / موبایل پیدا کند (رقم فارسی و انگلیسی).
2. همان‌جا وضعیت را ببیند: پلن، پایان شمسی، بدهی، مانده/سقف هفته، داخل بودن، سانس، ورود مجاز است یا دلیل رد.
3. ورود / خروج / ابطال همان روز (منطق حضور فعلی را نشکن).
4. عضو جدید ثبت کند (نام، موبایل، سانس/جنس طبق مدل موجود) و کد FS- را سیستم بسازد.
5. فروش اشتراک اول (حداقل نصف؛ شروع امروز یا آینده، نه گذشته) + پرداخت نقد / کارت‌خوان / کارت‌به‌کارت.
6. قسط، تسویه و تمدید با همان قوانین Payments. این‌ها را نشکن: select تم تاریک (KI-004)، مبلغ با جداکننده و حروف (KI-005)، تمدید قابل انجام (KI-006)، پلن تمدید و تعویض عضو پایدار (KI-007).
7. آرشیو / فعال‌سازی دوباره (حذف نیست).

ورود و خروج فقط منشی. مدیر می‌تواند حضور را ببیند و همان روز ابطال کند؛ ثبت ورود/خروج برای مدیر ممنوع بماند.

چیدمان پیشنهادی روی یک جریان، نه سه جزیره:

- پیدا کردن / انتخاب عضو
- کارت وضعیت همان عضو
- کارهای همان لحظه: ورود یا خروج · پرداخت/تمدید · فروش اگر اشتراک جاری ندارد
- ثبت عضو جدید
- لاگ امروز / داخل سالن

`/secretary/payments` می‌تواند به‌صورت لینک بماند، ولی کار روزمره از خانهٔ منشی گم نشود.
چیدمان دسکتاپ کمی جادار (`desk-shell-wide` مثل مدیر). موبایل نشکند.
بخش‌ها با عنوان واضح جدا باشند. شلوغی اضافه نساز.

## ظاهر همین قطعات
بازطراحی کل سایت ممنوع. برای همین صفحه:

- پیام خوانا، رنگ موفقیت و خطا مثل بقیهٔ پنل، نه یک بنر غول‌پیکر بالای همه‌چیز.
- صفحه‌بندی هم‌خانوادهٔ مدیر، نه سه دکمهٔ چسبیده.
- فاصلهٔ بخش‌ها طوری که منشی قاطی نکند کدام دکمه مال کدام کار است.
- تم روشن و تاریک هر دو. تاریخ شمسی. عدد فارسی.
- اگر برای خالی نبودن صفحه تصویر کوچک لازم شد، خودت هم‌خوان با برند بساز (`docs/visual-assets.md`). لوگو و عکس تزئینی الکی نگذار.

## تست
- تست واحد/API اگر ثبت عضو یا فروش منطق تازه شد.
- رقم فارسی و انگلیسی برای موبایل و مبلغ.
- دادهٔ نمونه: صفحه خالی ممنوع. اگر عضو بدون اشتراک جاری برای فروش اول در seed نیست، یکی اضافه کن و در `docs/sample-data.md` بنویس.
- مرورگر، خودت: جستجو؛ ورود؛ خروج؛ ابطال — هر بار ببین پیام کنار همان کار است نه بالای صفحه.
- جستجویی که بیش از یک صفحه نتیجه دارد؛ لاگ امروز اگر بلند است. ورق بزن. اسم صفحهٔ اول زیر دکمه نرود.
- تم روشن و تاریک.
- regression: سقف هفته، بدهی روز ۱۵، ابطال، مدت حضور (KI-003)، پرداخت، پلن تمدید که برنگردد، تعویض عضو، پنل مدیر (نمودار، تقویم، قیمت سایت، لینک پرداخت همان عضو).
- تست قرمز را push نکن.
