# ADR-0003: استک تکنولوژی (فرانت‌اند، بک‌اند، دیتابیس)

- Status: Accepted
- Date: 2026-10-08

## Context

باید برای فیت‌استیل یک استک انتخاب شود که:

- سایت عمومی + سه پنل (عضو / منشی / ادمین) را پوشش دهد
- RTL فارسی و تاریخ شمسی را خوب پشتیبانی کند
- قوانین دامنه (سقف هفتگی، وضعیت اشتراک، بدهی، نقش‌ها) را در بک‌اند امن اعمال کند
- برای یک تیم کوچک سریع قابل ساخت و نگهداری باشد
- مسیر PWA بعدی را نبندد
- دادهٔ رابطه‌ای (اعضا، اشتراک، حضور، پرداخت، پرسنل) را درست مدل کند

گزینه‌های بررسی‌شده (خلاصه):

| لایه | گزینه‌ها | نتیجه |
|------|----------|--------|
| فرانت | Next.js / Nuxt / SPA خالص (Vite+React) | Next.js |
| بک‌اند | Route Handlers داخل Next / NestJS جدا / Django | NestJS جدا |
| دیتابیس | PostgreSQL / MySQL / MongoDB | PostgreSQL |
| ORM | Prisma / TypeORM / Drizzle | Prisma |
| Auth | Session+OTP / JWT خالص / فقط پسورد | Session cookie + OTP موبایل برای عضو |

## Decision

### فرانت‌اند

**Next.js (App Router) + TypeScript + Tailwind CSS**

- سایت عمومی با SSR/SSG سریع و SEO-friendly
- پنل‌ها به‌صورت اپلیکیشن وب داخل همان پروژه (`/member`, `/secretary`, `/admin`)
- TypeScript برای ایمنی دامنه و API
- Tailwind برای پیاده‌سازی سریع دیزاین Cyan Night و ریسپانسیو
- ساختار طوری نگه داشته می‌شود که بعداً PWA قابل اضافه شدن باشد

کتابخانه‌های کمکی پیشنهادی (جزئیات پیاده‌سازی، نه تصمیم قفل‌شدهٔ جدا):

- UI icons / فرم‌ها بر اساس نیاز
- `dayjs` یا معادل + پلاگین جلالی برای تاریخ شمسی در UI
- فونت فارسی وب (مثلاً Vazirmatn)

### بک‌اند

**NestJS + TypeScript (API جدا) + Prisma**

- دامنه باشگاه منطق تجاری غنی دارد (اجازه ورود، سقف هفته، بدهی، شیفت). این منطق بهتر است در یک API لایه‌بندی‌شده باشد، نه پراکنده داخل UI.
- NestJS ماژول‌های واضح می‌دهد: `members`, `subscriptions`, `attendance`, `payments`, `staff`, `auth`
- فرانت Next.js فقط مصرف‌کنندهٔ API است → بعداً اگر PWA یا کلاینت دیگری آمد، همان API می‌ماند
- ارتباط فرانت و بک‌اند روی HTTP/JSON (REST در MVP)

احراز هویت:

- **اعضا**: ورود با موبایل + OTP پیامکی (الگوی رایج ایران)
- **منشی / ادمین**: نام کاربری/رمز یا OTP + session امن (cookie httpOnly ترجیحاً از طریق BFF ساده در Next یا cookie از API با CORS درست)
- کنترل دسترسی نقش‌محور (RBAC): `member` | `secretary` | `admin` (و در صورت نیاز بعدی `trainer`)

### دیتابیس

**PostgreSQL**

دلیل اصلی: داده کاملاً رابطه‌ای است — عضو ↔ اشتراک ↔ پلن ↔ حضور ↔ پرداخت ↔ پرسنل. نیاز به تراکنش، قید یکپارچگی، و گزارش مالی وجود دارد. MongoDB برای این دامنه مناسب نیست.

Prisma به‌عنوان ORM/migration tool روی PostgreSQL استفاده می‌شود.

### استقرار (جهت‌گیری اولیه)

- فرانت و API به‌صورت جداگانه deploy می‌شوند (دو سرویس)
- PostgreSQL به‌صورت سرویس managed یا روی همان سرور (بسته به میزبانی ایران/خارج؛ جزئیات هاستینگ در ADR بعدی در صورت نیاز)

## خلاصهٔ استک پذیرفته‌شده

```text
Frontend:  Next.js (App Router) + TypeScript + Tailwind CSS
Backend:   NestJS + TypeScript + Prisma
Database:  PostgreSQL
Auth:      OTP (اعضا) + Session/RBAC (پرسنل و پنل‌ها)
Client:    Web responsive only (PWA later optional)
```

## Consequences

### مثبت
- جداسازی UI و قوانین کسب‌وکار؛ تست‌پذیری بهتر برای حضور و مالی
- یک زبان (TypeScript) در کل استک
- PostgreSQL برای گزارش و قیدهای اشتراک/حضور مناسب است
- مسیر رشد به PWA بدون عوض کردن بک‌اند باز است

### هزینه / ریسک
- دو پروژه برای اجرا (Next + Nest) به‌جای یک فول‌استک ساده — برای این دامنه قابل قبول است
- نیاز به طراحی CORS/Auth بین فرانت و API
- وابستگی به سرویس SMS برای OTP اعضا

### خارج از این ADR
- انتخاب درگاه پرداخت / فقط ثبت دستی پرداخت پذیرش
- انتخاب ارائه‌دهنده SMS
- جزئیات مدل داده (در مستند دامنه / migrationهای Prisma ثبت می‌شود)
