## قانون اصلی

هر تغییری در پروژه — حتی کوچک — باید روی GitHub هم به‌روز شود.

عامل (Agent) موظف است بدون یادآوری تکراری مالک:

1. تغییرات را commit کند (با پیام واضح و کوتاه)
2. به GitHub **push** کند تا ریپو همیشه هم‌تراز لوکال باشد
3. وقتی لازم است **نسخه‌بندی (version / tag)** انجام دهد

مالک نباید مجبور شود هر بار بگوید «کامیت کن / پوش کن / ورژن بزن».

---

## چه چیزهایی commit نشوند

- فایل‌های `.env` و `.env.local` و هر رمز/کلید واقعی
- `node_modules/` و خروجی build
- فایل‌های موقتی سیستم

نمونهٔ امن برای env: فقط `.env.example`

---

## نسخه‌بندی (SemVer ساده)

فرمت: `MAJOR.MINOR.PATCH` — مثال: `0.1.0`

| چه وقت | چه کار |
|--------|--------|
| اسکلت اولیه / آماده‌سازی | `0.1.0` |
| فیچر قابل‌استفاده جدید (مثلاً پنل منشی) | MINOR بالا برود → `0.2.0` |
| باگ‌فیکس یا اصلاح کوچک بعد از یک نسخه | PATCH → `0.2.1` |
| تغییر بزرگ ناسازگار (به‌ندرت در MVP) | MAJOR → `1.0.0` |

موقع نسخه‌بندی:

1. فایل `VERSION` در ریشه را به‌روز کن
2. در صورت نیاز نسخهٔ `web/package.json` و `api/package.json` را هم‌تراز کن
3. git tag بزن: `v0.1.0`
4. tag را هم push کن: `git push origin v0.1.0` (یا `git push --tags`)

## جریان کاری بعد از هر کار معنادار

```text
تغییر کد روی لوکال → تست‌ها (اگر تغییر مهم بود) → commit → push به origin
اگر نقطهٔ عطف محصولی بود → bump VERSION + tag + push tag
اگر لوکال اوکی بود → آپدیت سرور زنده (بدون پاک کردن داده)
```

اگر تغییر مهم بود و تست قرمز است، تا سبز شدن push نکن. جزئیات: `docs/testing.md`

از ۱۴۰۴/۰۸/۱۱ سایت روی `https://fitclubapp.shop` باز است. **push به گیت کافی نیست**؛ همان تغییر باید روی سرور هم بیاید. اول لوکال، بعد سرور. → `docs/live-updates.md`
